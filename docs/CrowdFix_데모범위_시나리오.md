## 1. 기본 원칙

1. **시연에 나오는 기능은 실제로 동작해야 한다.** 화면만 만들고 뒤를 하드코딩하지 않는다.
2. **시연에 나오지 않는 기능은 새로 손대지 않는다.** 이미 구현된 기능은 그대로 둔다.
3. **시연 환경**: 자동 전달 기준값 T = 3, 메일은 시험용 수신함으로 보낸다(SRS 2.5, BR-07).
4. **플랫폼**: 모바일 웹(SRS 1.4). 학생 화면은 모바일 폭(약 390px), 운영자 화면은 데스크톱 폭으로 보여준다.
5. **의제 유형**: 등록과 참여는 Issue만 다룬다. Proposal은 목록의 Proposal 탭에서 조회만 하고, 등록·참여는 같은 구조로 동작한다고 발표에서 설명한다.

| 시점 | 나도 겪었어요 | 개선이 필요해요 | 고유 인원 |
|---|---|---|---|

### 2.5 참여 집계 규칙

- 공감 인원은 버튼('나도 겪었어요', '개선이 필요해요')으로만 집계한다. 글 작성이나 Report 연결만으로는 늘지 않는다(BR-03).
- 한 사람이 두 버튼을 모두 눌러도 고유 참여 인원은 1명이다(BR-03).
- Report 작성자와 버튼을 누른 사용자는 자동으로 구독된다(FR-NOTI-02).

## 3. 시연 시나리오 (약 4분, 5장면)

### 사전 준비
- 시드 데이터 초기화 스크립트로 2.4의 상태를 만든다. 메인 의제는 없어야 한다.
- 학생 A, 학생 B, 운영자, 시험 메일 수신함 화면을 준비한다. 학생 A의 알림함은 비어 있어야 한다.

### 장면 1. 탐색과 새 이슈 등록 — 학생 A (70초)
같은 프린터 문제를 겪은 학생 A와 B 중, A가 먼저 CrowdFix를 연다.

1. 메인 지도에 의제가 있는 건물 3곳의 마커가 표시된다.
2. 상태 필터를 `In Progress`로 바꾸면 마커와 목록이 함께 줄어든다. 필터를 해제한다.
3. 목록 → Proposal 탭으로 바꿔 "학점포기제도 개선" 등 제안 의제를 보여준다. (조회만)
4. 삼성학술정보관을 눌러 의제 목록을 본다. Wi-Fi, 콘센트 의제만 있고 **프린터 이슈는 없다.**
5. 글쓰기 화면에서 장소 `삼성학술정보관`을 선택하고 **"디도 B1 프린터에서 출력이 안 돼요"**를 입력한 뒤, 프린터 오류 화면 **사진 1장을 첨부**한다.
6. 비슷한 의제가 없으므로 새 의제로 등록된다. 의제 상세의 Report에 사진 썸네일이 표시된다. A가 '나도 겪었어요'를 누른다. 고유 참여 인원 1.

**전달할 메시지**: 시설 문제와 제도 제안을 한 곳에서 보고, 이미 알려진 문제가 없으면 하나의 입구에서 바로 새 의제로 등록한다. (Proposal PAIN 02, 05)

### 장면 2. AI 추천과 통합, 참여 — 학생 B (60초)
그 사이 다른 학생 1명이 참여해 고유 인원은 2명인 상태다.

1. B가 글쓰기 화면에서 장소 `삼성학술정보관`을 선택한다.
2. 본문에 **"디도 지하 프린터에서 용지 걸림 오류 화면이 떠요"**를 입력한다.
3. 작성 중에 "비슷한 의제가 있어요" 카드가 뜨고, **A가 등록한 디도 B1 프린터 의제**가 1순위로 추천된다.
   - 같은 건물의 Wi-Fi 의제, 다른 건물(제1공학관21동)의 프린터 의제는 추천되지 않는다.
4. '이 의제에 참여'를 눌러 통합하면 해당 의제 상세 화면으로 이동하고, B의 글이 연결된 Report 목록에 추가된다.
5. **'나도 겪었어요'와 '개선이 필요해요'를 둘 다 누르고**, 의제를 구독한다.

**전달할 메시지**: 표현이 달라도 같은 문제는 하나의 의제로 묶이고, 장소나 대상이 다르면 구분된다. (Proposal 주요 기능 ③, PAIN 03)

### 장면 3. 메일 전달 — 의제 상세 → 메일 수신함 (40초)
1. B의 참여로 고유 참여 인원이 **2 → 3**이 된다. 두 버튼을 다 눌렀지만 1명만 증가한다.
2. 고유 인원이 T(3)에 도달해 **'전달 완료'** 표시가 뜬다. 처리 상태는 Backlog로 유지된다(SRS 4.4.2 ①).
3. 시험 메일 수신함에 보고서 메일이 한 건 도착해 있다.
   - 포함 항목: 요약, 위치, 참여 규모(경험자 3 · 개선 요청 1 · 고유 3명), 대표 Report, 원문 링크

**전달할 메시지**: 한 사람은 한 명으로만 세고, 기준에 도달하면 근거가 정리된 보고서 한 건이 담당 조직에 전달된다. (SRS BR-03)

### 장면 4. 완료 처리 — 운영자 (45초)
1. 운영자 계정으로 의제 상세 화면에 들어간다.
2. 상태를 `In Progress`로 바꾸고 사유 "시설팀 확인 중"을 입력한다.
3. 상태를 `Done`으로 바꾸고 결과 "부품 교체 완료"를 입력한다.
4. 상태 변경 이력이 의제 상세 화면에 표시된다.

**전달할 메시지**: 처리 과정과 결과가 공개적으로 기록된다.

### 장면 5. 알림함 — 학생 A (20초)
1. 처음 제보한 학생 A의 알림함에 프린터 의제 완료 알림이 와 있다. (작성자 자동 구독)
2. 알림을 누르면 상세 화면에서 처리 결과를 확인할 수 있다.

**전달할 메시지**: 제보한 학생이 결과까지 확인할 수 있다. (Proposal PAIN 04)

## 5. 완료 기준

- [ ] 비슷한 의제가 없으면 A의 글이 새 의제로 생성되고 지도에 바로 반영된다.
- [ ] 첨부한 사진이 의제 상세에 표시되고, 서버를 재시작해도 사라지지 않는다 (Docker 볼륨 저장).
- [ ] 방금 생성된 A의 의제가 B의 글 작성 중에 1순위로 추천된다 (새 의제도 즉시 검색 대상이 된다).
- [ ] 추천 카드는 본문 입력 중에 뜬다 (등록 버튼을 누르기 전).
- [ ] 글 작성이나 Report 통합만으로는 고유 인원이 늘지 않는다.
- [ ] B가 두 버튼을 모두 눌러도 고유 참여 인원은 1만 증가한다 (2 → 3).
- [ ] 3번째 고유 참여에서 메일이 정확히 한 번 발송된다. 버튼을 연타하거나 취소 후 다시 눌러도 두 번 발송되지 않는다.
- [ ] 운영자의 상태 변경이 학생 화면에 반영되고, 작성자(학생 A) 알림함에 알림이 생성된다.
- [ ] 초기화 스크립트로 2.4의 상태를 반복해서 만들 수 있다.
- [ ] 장면 1~5가 처음부터 끝까지 끊기지 않고 동작한다.

### AI 테스트 문장

메인 의제는 "디도 B1 프린터에서 출력이 안 돼요"(장소: 삼성학술정보관)로 먼저 등록한 상태에서 확인한다.

| 입력 문장 | 기대 결과 |
|---|---|
| 디도 지하 프린터에서 용지 걸림 오류 화면이 떠요 (장소: 삼성학술정보관) | 디도 B1 프린터 의제로 연결 |
| B1 프린터 출력 안 돼요 (장소: 삼성학술정보관) | 디도 B1 프린터 의제로 연결 |
| 제1공학관 프린터 토너가 부족해요 (장소: 제1공학관21동) | 제1공학관21동 프린터로 연결, 디도 프린터와는 연결 안 됨 |
| 디도 B1 와이파이가 자꾸 끊겨요 (장소: 삼성학술정보관) | Wi-Fi 의제로 연결, 프린터 의제와는 연결 안 됨 |

**구현 메모**
- 임베딩 검색 전에 **선택한 건물로 후보를 먼저 거른다.**
- 새 의제를 등록하면 임베딩을 바로 저장해, 다음 글 작성 때 즉시 추천 대상이 되게 한다.
- 한국어를 지원하는 다국어 임베딩 모델을 사용하고, 서버 시작 시 모델을 미리 로드한다.
- 유사도가 애매하면 후보를 보여주고 사용자가 '참여 / 새 의제 등록' 중에서 고르게 한다.
