## 1. 기본 원칙

1. **시연에 나오는 기능은 실제로 동작해야 한다.** 화면만 만들고 뒤를 하드코딩하지 않는다.
2. **시연에 나오지 않는 기능은 새로 손대지 않는다.** 이미 구현된 기능은 그대로 둔다.
3. **시연 환경**: 자동 전달 기준값 T = 3, 메일은 시험용 수신함(Mailpit, http://localhost:8025)으로 보낸다(SRS 2.5, BR-07).
4. **플랫폼**: 모바일 웹(SRS 1.4). 학생 화면은 모바일 폭(약 390px)으로 보여준다. 넓은 화면(웹)에서는 가운데 앱 칸(최대 430px) 안에서만 화면과 전환 효과가 그려진다. 운영자 화면도 같은 앱 칸 안에서 보여준다(Increment 5에서 기존 상세 화면·전환 효과를 그대로 쓰기로 함).
5. **의제 유형**: **등록은 Issue만** 다룬다. Proposal은 목록·지도에서 조회하고, **'나도 원해요'로 참여할 수 있다**(카드와 상세 화면). Proposal 등록은 같은 구조로 동작한다고 발표에서 설명한다.

### 2.5 참여 집계 규칙

- 공감 인원은 버튼('나도 겪었어요', '개선이 필요해요', '나도 원해요')으로만 집계한다. 글 작성이나 리포트 통합만으로는 늘지 않는다(BR-03).
- 한 사람이 두 버튼을 모두 눌러도 고유 참여 인원은 1명이다(BR-03). 같은 버튼 연타·동시 요청도 1건만 저장된다(DB 고유 제약).
- 버튼을 다시 누르면 참여가 취소되고, 남은 참여 기록으로 고유 인원을 다시 센다.
- Report 작성자와 버튼을 누른 사용자는 자동으로 구독된다(FR-NOTI-02). 구독을 직접 해제한 사용자는 다시 자동 구독하지 않는다.
- 참여 버튼은 목록 카드와 상세 화면 하단 고정 영역 두 곳에 있고, 버튼 안에 집계가 함께 보인다(예: `나도 겪었어요 3`).

## 3. 시연 시나리오 (약 4분, 5장면)

### 사전 준비
- 시드 데이터를 초기화해 2.4의 상태를 만든다. 메인 의제는 없어야 한다.
  ```bash
  docker compose exec api python -m app.seed
  ```
- 시험 메일 수신함을 비운다(`app.seed`는 메일함을 비우지 않는다). 기본 포트 기준:
  ```bash
  curl -X DELETE http://localhost:8025/api/v1/messages
  ```
- 학생 A, 학생 B, 운영자는 **브라우저 프로필(또는 시크릿 창)을 따로** 쓰거나 장면마다 로그인 계정을 바꾼다. 같은 프로필의 탭은 로그인 정보를 공유해 화면에 보이는 계정과 실제 요청 계정이 달라질 수 있다.
- 학생 A의 알림함은 비어 있어야 한다. 시드의 '21동 프린터' 의제는 고유 2명·미전달이므로 촬영 중 참여 버튼을 누르지 않는다(누르면 별도 메일 발송).
- 장면 1의 첨부 사진: `data/demo/printer_error.png` (실제 프린터 오류 사진으로 바꿔도 된다)

### 장면 1. 탐색과 새 이슈 등록 — 학생 A (70초) ✅
같은 프린터 문제를 겪은 학생 A와 B 중, A가 먼저 CrowdFix를 연다.

1. 메인 지도에 의제가 있는 건물 3곳의 핀 마커가 표시된다.
2. 상태 필터를 `진행 중`으로 바꾸면 마커와 목록이 함께 줄어든다. `진행 중`을 다시 누르거나 `전체`를 눌러 해제한다. (상태 필터는 한 번에 하나만 선택된다)
3. 목록 → Proposal 탭으로 바꿔 "학점포기제도 개선" 등 제안 의제를 보여준다. (지도 탭 목록의 맨 아래에서도 보인다)
4. 삼성학술정보관 마커를 눌러 의제 목록을 본다. Wi-Fi, 콘센트 의제만 있고 **프린터 이슈는 없다.**
5. 오른쪽 아래 연필 버튼(글쓰기)을 누른다. 장소 `삼성학술정보관`을 선택하고 **"디도 B1 프린터에서 출력이 안 돼요"**를 입력한 뒤, 프린터 오류 화면 **사진 1장을 첨부**한다.
   - 작성 중 추천 영역에 "비슷한 의제가 없어요."가 나온다(같은 건물의 Wi-Fi 의제는 대상이 달라 추천되지 않음).
6. 등록하면 "새 의제로 등록했어요." 안내와 함께 의제 상세로 이동한다. 층(B1)은 본문에서 자동으로 잡히고, Report에 사진 썸네일이 표시된다. A는 자동 구독된다. A가 '나도 겪었어요'를 누른다. 고유 참여 인원 1.

**장면 사이**: 화면 밖에서 C1이 참여한다 (고유 인원 1 → 2).
```bash
docker compose exec api python -m app.demo c1-join
```

**전달할 메시지**: 시설 문제와 제도 제안을 한 곳에서 보고, 이미 알려진 문제가 없으면 하나의 입구에서 바로 새 의제로 등록한다. (Proposal PAIN 02, 05)

### 장면 2. AI 추천과 리포트 통합, 참여 — 학생 B (60초) ✅
그 사이 다른 학생 1명이 참여해 고유 인원은 2명인 상태다.

1. B가 글쓰기 화면에서 장소 `삼성학술정보관`을 선택한다(검색창에 '디도'를 입력해도 찾아진다).
2. 본문에 **"디도 지하 프린터에서 용지 걸림 오류 화면이 떠요"**를 입력한다.
3. 본문이 5자를 넘으면 "비슷한 의제를 찾는 중" 표시 후 **"비슷한 의제가 있어요"** 카드가 떠오르고, **A가 등록한 B1 프린터 의제**가 '같은 문제'로 1순위 추천된다. 근거로 `일치: 건물, 대상(프린터)`가 보인다.
   - 같은 건물의 Wi-Fi 의제, 다른 건물(제1공학관21동)의 프린터 의제는 추천되지 않는다.
   - (선택) 추천 카드를 누르면 글쓰기 화면을 그대로 둔 채 그 의제의 상세가 위에 겹쳐 열리고, 뒤로가기로 닫으면 쓰던 글이 그대로 남아 있다.
4. **'이 의제에 리포트 통합하기'**를 누르면 해당 의제 상세 화면으로 이동하고("기존 의제에 내 글을 연결했어요."), B의 글이 연결된 Report 목록에 추가된다. 리포트 통합만으로는 고유 인원이 늘지 않는다(2 유지). B는 자동 구독된다(`구독 중`).
5. 하단의 **'나도 겪었어요'를 먼저 누르고, 이어서 '개선이 필요해요'를 누른다.** 경험 3 · 공감 1 · 고유 3 (장면 3).

**전달할 메시지**: 표현이 달라도 같은 문제는 하나의 의제로 묶이고, 장소나 대상이 다르면 구분된다. (Proposal 주요 기능 ③, PAIN 03)

### 장면 3. 메일 전달 — 의제 상세 → 메일 수신함 (40초) ✅
1. B가 '나도 겪었어요'를 누르면 고유 참여 인원이 **2 → 3**이 되고, 그 순간 전달 상태가 새로고침 없이 **'미전달' → '전달 완료'**로 바뀐다. 처리 상태는 검토 대기로 유지된다(SRS 4.4.2 ①).
2. 이어서 '개선이 필요해요'를 눌러도 고유 인원은 3명 그대로다. 메일도 다시 발송되지 않는다.
3. 시험 메일 수신함에 보고서 메일이 한 건 도착해 있다.
   - 포함 항목: 요약, 위치, 참여 규모, 대표 Report와 연결된 Report, 원문 링크
   - 참여 규모는 **발송 순간 값**이라 메일에는 `경험자 3 · 개선 요청 0 · 고유 3명`으로 적힌다. 상세 화면은 두 번째 버튼까지 반영해 경험 3 · 공감 1 · 고유 3이다.

> 구현 메모(`api/app/delivery.py`): 참여 등록 API가 의제 행을 잠근(`SELECT … FOR UPDATE`) 트랜잭션에서 고유 인원과 전달 상태를 확인하고, 기준에 처음 도달하면 전달 상태를 '전달 완료'로 바꾸고 발송 기록(`deliveries.result = pending`)을 남겨 **참여와 함께 커밋한 뒤** SMTP로 보낸다. 결과는 `accepted`/`no_response`로 기록하고, 실패하면 '전달 실패'로 바꾼다. 담당 조직은 의제의 대상 분류(`category`)와 연결표(`org_routes`)로 정한다.
> 보장 범위: 의제당 **최대 한 번** 보낸다. 커밋이 실패하면 예약도 취소돼 메일이 나가지 않는다. 발송 실패나 예약 후 서버 중단(`pending`으로 남음)은 자동으로 다시 보내지 않는다(메일 재시도는 구현 제외, 4.2).

**전달할 메시지**: 한 사람은 한 명으로만 세고, 기준에 도달하면 근거가 정리된 보고서 한 건이 담당 조직에 전달된다. (SRS BR-03)

### 장면 4. 완료 처리 — 운영자 (45초) ✅
1. 운영자 계정으로 목록에서 프린터 의제를 연다. 운영자에게는 하단 참여 버튼 대신 **'운영자 처리'** 영역이 보인다.
2. 사유 "시설팀 확인 중"을 입력하고 **'진행 중으로 변경'**을 누른다.
3. 처리 결과 `해결`, 처리 내용 "부품 교체 완료"를 입력하고 **'완료 처리하고 결과 공개'**를 누른다. (완료에는 결과와 내용이 필수, 학생 계정의 변경 요청은 403)
4. 상태 변경 이력이 의제 상세 화면의 '처리 이력'에 표시된다. 완료된 의제는 하단 고정 영역에 **"문제가 해결되었어요."**가 표시된다(이미 구현됨).

**전달할 메시지**: 처리 과정과 결과가 공개적으로 기록된다.

### 장면 5. 알림함 — 학생 A (20초) ✅
1. 학생 A 화면을 새로 열거나 새로고침하면(열린 화면에는 자동으로 들어오지 않음) 상단 종 아이콘에 **2**가 표시된다. 진행 시작·결과 공개 알림 두 건이다. 같은 의제를 구독한 B도 같은 알림을 받는다.
2. 종 아이콘 → 알림함 → **'처리 결과'** 알림을 누르면 알림함 위에 상세가 겹쳐 열리고, "해결 · 부품 교체 완료"와 "문제가 해결되었어요."를 확인할 수 있다. 읽은 알림은 종 아이콘 숫자에서 빠진다.

**전달할 메시지**: 제보한 학생이 결과까지 확인할 수 있다. (Proposal PAIN 04)

### AI 추천 규칙 (TBD-06)

1. **선택한 건물로 후보를 먼저 거른다.** 다른 건물의 의제는 비교하지 않는다. 완료된 의제와 Proposal은 후보에서 뺀다.
2. 다국어 문장 임베딩 모델 `paraphrase-multilingual-MiniLM-L12-v2`로 의제 제목·연결된 Report 본문과 코사인 유사도를 비교한다(pgvector). 모델은 서버 시작 시 미리 로드한다.
3. 본문에서 **대상**(프린터·Wi-Fi·콘센트·냉난방)을 뽑아, 의제와 대상이 다르면 유사도가 높아도 추천하지 않는다.
4. 글과 의제 모두 **강의실 번호**가 있으면 번호가 같아야 추천한다(예: 26312 ≠ 26208).
5. 판정 기준(값은 `api/app/config.py`의 `similar_*`):

| 조건 | 같은 문제 | 관련 있음 |
|---|---|---|
| 대상이 같음 | 유사도 0.55 이상 | 0.40 이상 |
| 대상을 알 수 없음 | 0.85 이상 | 0.80 이상 |

6. 연결은 항상 사용자가 '이 의제에 리포트 통합하기'를 눌러야 되며, 근거(유사도·일치한 속성)를 `report_links`에 기록한다.
